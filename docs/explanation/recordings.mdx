# Recordings

_Understanding how Fishjam captures composed media as files_

A **recording** captures media rendered inside a [composition](./compositions) and stores it as an MP4 file. A composition is a live process: it produces media while it runs and leaves nothing behind once it is deleted. A recording is the persistent artifact of that process. It remains available after the composition and the room it was created from are gone, and Fishjam keeps it for [3 months](#retention).

What a recording captures is set by its **source**. There are two kinds:

- A **template recording** renders its own scene from a React template. It is not bound to any output or live stream, and the recording is the only thing it produces. This is the default way to record.
- A **composition recording** mirrors an output that the composition already publishes, such as the one feeding a livestream. Use it to keep a copy of a live stream you are already running.

## Template recordings

```text
inputs ──▶ composition ──template──▶ recording ──▶ MP4 ──▶ [download]
```

A template recording still runs inside a composition. The composition is the workspace that holds your inputs, whether you register them yourself or forward a Fishjam room into it. The template decides how those inputs are rendered into the file, and nothing is published live: no output is registered and no livestream is needed.

The template is a React component, written and bundled exactly like the [template of an output](./../how-to/compositions/write-and-deploy-a-template). It drives the scene on its own: the hooks from `@fishjam-cloud/composition` give it the live state of a forwarded room, and the `eventBus` delivers any payloads your backend [sends to the composition](./../how-to/compositions/drive-a-template-with-events). You upload the bundle, at most 1 MiB, together with the request that creates the recording.

Besides the composition URL, a template recording accepts two options: `resolution`, the size the template is rendered at (1280x720 by default), and `audio`, which can be set to `false` for a video-only file. A composition can run several template recordings at once, each with its own template.

## Composition recordings

```text
composition ──output──▶ livestream / RTMP ──▶ [viewers]
                │
                └──recording──▶ MP4 ──▶ [download]
```

A composition produces media through its outputs, and a composition recording captures one of them. To create one, you specify a composition and one of its registered outputs, and Fishjam attaches a recorder to that output. The recorder captures the output as it is published: the same layout and resolution, including every scene update, encoded separately from the live stream. If the recorded file should differ from the live stream, use a template recording instead.

Besides composition URL and output ID, a composition recording accepts a single option, `scaleRatio`, which sets the recording resolution as a fraction or multiple of the output's resolution. For example, `0.5` stores the recording at half the output resolution.

An output can have at most one recording at a time. To record the same output again, wait until the current recording is no longer `active`.

## Composition API and Server API

Compositions are managed through the [Composition API](./../api/reference#compositions), while recordings are created and managed through the [Fishjam Server API](./../api/reference#server), either directly or with the JS and Python server SDKs. This split reflects ownership: a composition is a running session that you configure, whereas a recording is a resource of your Fishjam app, stored alongside your rooms and livestreams and managed with the same management token. You do not call the Composition API to record; the Server API controls the capture inside the composition on your behalf, including loading the template of a template recording.

## Lifecycle

A recording has four statuses:

| Status      | Meaning                                                 |
| ----------- | ------------------------------------------------------- |
| `active`    | Media is being captured.                                |
| `finished`  | Capture has ended and the file is being prepared.       |
| `available` | The MP4 is ready and `files` contains the download URL. |
| `failed`    | An error occurred and no file will be produced.         |

Capture starts as soon as the recording is created. It ends when you stop the recording explicitly, or automatically when its composition ends: when you delete the composition, or when it [cleans itself up](./compositions#cost-and-lifecycle) after five minutes without input media. A composition recording also ends when the recorded output ends. Finalization is asynchronous: the recording remains `active` until capture has ended, then transitions through `finished` to `available` once the file is ready.

Every status change emits a `RecordingStatusChanged` [server notification](./../api/reference#protobufs) over your configured webhook or a websocket, so you can react to a file becoming available without polling.

Once a recording is `available`, its `files` field lists the media files in playback order as direct HTTPS URLs that you can download or serve to your users. To remove a recording and its files before they expire, delete the recording. A recording cannot be deleted while it is `active`.

## Retention

Fishjam keeps a recording and its files for 3 months after the recording is created. After that they are no longer available through the API, so download any file you need to keep for longer. For up to 6 months after creation, an expired recording can still be retrieved on request: contact us at `contact@fishjam.io`.

## Metadata

A recording carries optional free-form `metadata`, set at creation and returned with every read. Because recordings accumulate over time, metadata also serves as the primary way to locate them: listing recordings supports filtering by metadata pairs, for example to retrieve every recording for a given show or customer.
